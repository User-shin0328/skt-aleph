# 카드 2: 패스키 등록 및 공개키 저장 실증 보고서

## 1. 개요 및 등록 흐름
패스키 등록은 **비밀번호를 일체 사용하지 않고**, 기기(Authenticator) 내부의 하드웨어 보안 영역(Secure Enclave, TPM, 또는 FIDO2 보안키)에서 비대칭 키 쌍(공개키-개인키)을 생성한 후, **공개키(Public Key)만 서버로 전송하여 저장**하는 FIDO2 / WebAuthn 표준 등록 절차입니다.  
개인키(Private Key)는 기기 밖으로 절대 나가지 않으며 서버에도 전송되지 않습니다.

```
[클라이언트]                           [서버: api/passkey.js]
     |                                          |
     |---- 1. POST ?action=register_options --->|
     |                                          |-- 32바이트 일회용 난수 Challenge 생성
     |<--- 2. challenge, rp, user, pubKeyCred --|   (서버 활성 맵에 60초 TTL 보관)
     |                                          |
     |-- 3. navigator.credentials.create()      |
     |   (기기 하드웨어에서 P-256 키 쌍 생성)       |
     |   (개인키는 기기 내부에 영구 보관)            |
     |                                          |
     |---- 4. POST ?action=register_verify ---->|
     |   (공개키 JWK, credentialId, 이름 전송)    |-- 챌린지 일치 확인 및 1회용 소모
     |                                          |-- 공개키 DB 저장 (개인키 전송 없음)
     |<--- 5. 201 Created (등록 완료 응답) -------|
```

## 4. 서버에 저장된 값과 공개키 보관 증적

서버 데이터베이스(`passkey_db.json`)에 등록된 사용자 레코드는 다음과 같이 저장됩니다:
- **저장된 값**: 식별자(`id`), 사람이 알아볼 수 있는 이름(`name`), 등록일시(`createdAt`), 서명 카운터(`signCount`), 그리고 **비대칭 타원곡선 공개키(`publicKeyJwk`)**입니다.
- **비밀번호와의 본질적 차이**:
  - 비밀번호는 지식 기반(Knowledge-based) 비밀값이므로 유출 시 누구나 사칭이 가능합니다.
  - 반면 서버에 저장된 값은 누구나 보아도 무방한 **수학적 공개키(x, y 좌표)**일 뿐이며, 기기 내부에 보관된 개인키 없이는 서명을 위조할 수 없습니다. 따라서 서버 데이터베이스가 통째로 탈취당하더라도 공격자는 로그인할 수 없습니다.

## 5. 등록 취소 시의 예외 처리 및 저장소 보존

- 사용자가 브라우저 패스키 팝업창에서 [취소]를 누르거나 모달에서 [취소] 버튼을 클릭할 경우:
  - 브라우저 WebAuthn API가 `NotAllowedError` 또는 취소 이벤트를 발생시킵니다.
  - 클라이언트 화면에 `패스키 등록이 취소되었습니다` 안내 문구가 출력됩니다.
  - 서버로는 검증 요청(`register_verify`)이 전송되지 않으므로, 서버 데이터베이스에는 어떠한 불완전한 키나 데이터도 저장되지 않고 원본 상태가 100% 보존됩니다.

## 6. 패스키 저장소 위치 명시

등록된 패스키는 기기 및 환경에 따라 다음 세 곳의 하드웨어/클라우드 엔클레이브에 안전하게 보관됩니다:
1. **Google 비밀번호 관리자 (Google Password Manager)**: 안드로이드 및 크롬 브라우저 환경에서 E2EE(종단간 암호화)되어 동기화 보관
2. **기기 자체 내장 보안 하드웨어 (Secure Enclave / TPM)**: 맥북 Touch ID 및 윈도우 PC TPM 2.0 칩 내부에 하드웨어적으로 분리 격리
3. **물리적 외장 보안키 (YubiKey 5C NFC)**: FIPS 140-2 레벨 3 인증을 획득한 USB/NFC 외장 하드웨어 보안 토큰

## 7. 무인가 패스키 발급 및 임의 계정 생성 방지 대책

본 시스템은 불특정 다수가 자유롭게 가입하는 공개 포털이 아닌, **신재원 개인 소개 포트폴리오의 비공개 볼트**입니다. 따라서 누구나 무분별하게 패스키를 발급받거나 소유자 계정에 무단으로 키를 등록하는 공격을 원천 방지하기 위해 3단계 보안 통제를 적용했습니다:

1. **계정 화이트리스트 엄격 통제**:
   - `ALLOWED_USERS = ['runner_shin', 'reviewer_guest']`에 명시된 사전 인가 계정 외 임의 사용자명으로 패스키 등록을 시도할 경우 즉시 `HTTP 403 Forbidden` (`REGISTRATION_DISALLOWED`)으로 거절합니다.
2. **소유자(`runner_shin`) 신규 기기 등록 시 기존 패스키 세션 인증 필수**:
   - 외부 공격자가 소유자 계정(`runner_shin`)에 자신의 기기 패스키를 무단 등록하여 비공개 영역을 열어보는 공격을 방지하기 위해, 신규 패스키 등록 요청(`register_options`, `register_verify`) 시 반드시 기존에 등록된 패스키로 로그인된 유효한 세션(`Authorization: Bearer <JWT>`)이 있어야만 추가 등록이 허용됩니다 (`HTTP 401 Unauthorized` 차단).
3. **기기 분실 대비 패스키 등록 쿼터 제한**:
   - 패스키 무한 남발 및 DoS를 방지하기 위해 계정별 최대 등록 가능 패스키 개수를 제한(소유자 계정 최대 3개, 심사관 계정 최대 2개)하여 안전하게 관리합니다 (`HTTP 400 Bad Request`, `MAX_CREDENTIALS_REACHED`).
