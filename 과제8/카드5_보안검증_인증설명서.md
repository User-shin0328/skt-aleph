## 2. 인증 구현 설명서 (6대 핵심 항목)

### ① 무엇으로 붙였나 (인증 방식 및 기술 스택)
- **구현 방식**: 외부 서드파티 인증 서비스(Firebase, Auth0 등)에 의존하지 않고, **Node.js 내장 암호화 모듈(`crypto`)을 활용한 WebAuthn FIDO2 표준 프로토콜 직접 구현(Direct Implementation)** 방식을 채택했습니다.
- **클라이언트 기술**: 브라우저 W3C 표준 `navigator.credentials` (Web Authentication API) 및 W3C Web Crypto API (`crypto.subtle`)
- **암호화 알고리즘**:
  - 공개키 암호: **NIST P-256 (secp256r1) ECDSA** 타원곡선 전자서명 (ES256, alg: -7)
  - 일회용 질문 난수 생성: `crypto.randomBytes(32)`
  - 세션 식별자: HMAC-SHA256 기반 무상태 JWT Bearer Token

### ② 왜 그걸 골랐나 (선정 배경과 이유)
1. **비밀번호 유출 공격(크리덴셜 스터핑, 피싱) 원천 무력화**:
   - 비밀번호는 서버에 해시 형태로 저장되더라도 레인보우 테이블이나 무차별 대입, 피싱 사이트에 의해 노출될 위험이 상존합니다.
   - 반면 WebAuthn 패스키는 특정 도메인(RP ID)에 암호학적으로 귀속되며, 서버에는 오직 **공개키**만 저장되므로 서버 DB가 유출되어도 개인키가 없으면 로그인이 불가능합니다.
2. **사용자 경험의 극대화**:
   - 복잡한 비밀번호를 외우거나 입력할 필요 없이 기기 생체인증(지문, 얼굴인식) 또는 하드웨어 키 터치 한 번으로 1초 만에 안전하게 진입할 수 있습니다.
3. **독립적 제어권과 가벼운 번들**:
   - 무거운 외부 라이브러리 없이 순수 웹 표준 API와 서버리스 경량 백엔드로 구현하여 서버리스 콜드 스타트 지연을 최소화했습니다.

### ③ 어디를 어떻게 고쳤나 (4대 핵심 흐름 소스코드 위치)
등록·로그인·로그아웃·비공개 자료 조회의 4대 흐름이 지나는 정확한 소스코드 위치는 다음과 같습니다:

| 인증 흐름 | 프론트엔드 통과 지점 (`index.html`) | 백엔드 API 처리 지점 (`api/passkey.js`) | 핵심 처리 로직 |
|:---|:---|:---|:---|
| **1. 등록 흐름** | `submitPasskeyRegistration()` (라인 1470~1540) | `action === 'register_options'` 및 `action === 'register_verify'` (라인 175~305) | 32B 난수 챌린지 생성, 클라이언트 P-256 키 쌍 생성, 공개키 JWK 서버 DB 저장 (개인키 비전송) |
| **2. 로그인 흐름** | `executePasskeyLogin()` (라인 1555~1625) | `action === 'login_options'` 및 `action === 'login_verify'` (라인 310~460) | 매번 새 챌린지 발급, 공개키로 디지털 서명(`crypto.verify`) 검증, 챌린지 1회용 즉시 파기 후 JWT 발급 |
| **3. 로그아웃 흐름** | `handlePasskeyLogout()` (라인 1745~1770) | `action === 'logout'` (라인 575~590) | 세션 스토리지 토큰 삭제, 서버 블랙리스트(`revokedTokens`)에 토큰 등록하여 재사용 원천 차단 |
| **4. 비공개 자료 조회** | `loadSecretVault()` (라인 1630~1690) | `action === 'get_secrets'` (라인 465~505) | `Authorization: Bearer` 토큰 검증, 요청자 소유권(`owner === auth.username`) 대조 후 3대 비공개 자료 반환 |

### ④ 안 열리는 것을 확인한 기록 (4대 공격 차단 실증)
본 시스템은 웹 화면 내의 **[🛡️ 패스키 보안 검증 샌드박스 콘솔]**을 통해 아래 4가지 보안 차단을 누구나 실시간으로 검증할 수 있습니다:
1. **로그인 없이 비공개 볼트 열기** &rarr; `HTTP 401 Unauthorized` 차단 (자료 누출 0건)
2. **남의 패스키로 타인 볼트 열기 (IDOR)** &rarr; `HTTP 403 Forbidden` 차단 (변조 0건)
3. **이미 쓴 일회용 질문 재사용 (Replay)** &rarr; `HTTP 400 Bad Request (CHALLENGE_ALREADY_USED)` 차단
4. **기기 분실로 삭제된 패스키로 로그인** &rarr; `HTTP 401 Unauthorized (UNKNOWN_OR_DELETED_CREDENTIAL)` 차단

### ⑤ AI와 나 (역할 분담 및 직접 판단)
- **AI에게 맡긴 일**: W3C WebAuthn 레벨 3 명세에 따른 P-256 ECDSA 서명 데이터 직렬화/역직렬화 알고리즘 구현, 실시간 콘솔 터미널 UI 마크업 및 비공개 3대 항목 데이터 템플릿 생성
- **내가 직접 판단한 일**: 기기 분실이라는 패스키의 근본적 취약점을 보완하기 위해 '다중 패스키 등록 및 특정 패스키 삭제 후 잔여 키 로그인' 구조를 필수 아키텍처로 도입하고, 소개 페이지의 1번 공개 내용은 1px도 훼손되지 않도록 완벽히 유지하도록 통제함
- **AI 제안을 따르지 않은 일**: AI가 초기에 제안한 타사 상용 WebAuthn SaaS 연동 방식을 거부하고, 채점관이 시크릿 창에서도 즉시 검증할 수 있도록 순수 Node.js crypto 기반의 자체 경량 서버리스 API와 가상 시뮬레이터를 병행 탑재하도록 전면 수정함

### ⑥ 아직 못 막은 것 (최소 1개 구체적 명시)
- **기기 자체의 잠금 해제 우회 위험**:
  - 패스키는 기기의 잠금(PIN 번호, OS 비밀번호, 생체인증)을 통과한 사용자에게 서명 권한을 부여합니다.
  - 만약 공격자가 사용자의 스마트폰이나 노트북을 화면이 켜진 상태로 탈취하거나, OS의 로그인 PIN(예: 4자리 숫자)을 훔쳐본 상태라면 브라우저의 WebAuthn 프롬프트를 공격자가 직접 승인하여 패스키 로그인을 성공시킬 수 있습니다.
- **향후 보완 계획**:
  - 비공개 볼트 접근 시 기기 인증 외에도 '시간 기반 2단계 일회용 인증(TOTP)'을 결합한 다중 요소 인증(MFA) 레이어를 추가 구성할 계획입니다.

## 3. 계정 2개 분리 및 타인 자료 격리(IDOR 차단) 실증

시스템에는 서로 다른 비공개 데이터를 가진 2개의 계정이 등록되어 있습니다:
- **계정 1**: `runner_shin` (신재원 본인 계정) &rarr; eBPF 보안 엔진 메모, 테크 기업 분석, TCP 장애 회고 (총 3건)
- **계정 2**: `reviewer_guest` (심사관 게스트 계정) &rarr; 게스트 검증 메모 A, 게스트 검증 메모 B (총 2건)

### (1) 한쪽 패스키로 다른 쪽 비공개 자료 요청 시 차단 (`runner_shin` &rarr; `reviewer_guest`)
`runner_shin` 계정의 정상 토큰을 헤더에 담고, 쿼리 파라미터로 게스트의 비공개 자료를 요청한 경우:

```http
GET /api/passkey?action=get_secrets&owner=reviewer_guest HTTP/1.1
Host: skt-aleph-gilt.vercel.app
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6InJ1bm5lcl9zaGlu...[신재원 토큰]
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json; charset=utf-8

{
  "success": false,
  "error": "FORBIDDEN_DATA_ACCESS",
  "message": "접근 권한이 없습니다. 계정 [runner_shin]의 패스키로 타인 [reviewer_guest]의 비공개 볼트를 열 수 없습니다.",
  "requestedOwner": "reviewer_guest",
  "authenticatedUser": "runner_shin",
  "mutatedCount": 0
}
```

### (2) 반대 방향 요청 시 차단 (`reviewer_guest` &rarr; `runner_shin`)
반대로 게스트의 패스키 토큰으로 `runner_shin`의 비공개 자료를 요청한 경우:

```http
GET /api/passkey?action=get_secrets&owner=runner_shin HTTP/1.1
Host: skt-aleph-gilt.vercel.app
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6InJldmlld2VyX2d1ZXN0...[게스트 토큰]
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json; charset=utf-8

{
  "success": false,
  "error": "FORBIDDEN_DATA_ACCESS",
  "message": "접근 권한이 없습니다. 계정 [reviewer_guest]의 패스키로 타인 [runner_shin]의 비공개 볼트를 열 수 없습니다.",
  "requestedOwner": "runner_shin",
  "authenticatedUser": "reviewer_guest",
  "mutatedCount": 0
}
```

### (3) 거절 전후 데이터 건수 불변성 검증 (0건 변조)
- 공격 요청 전 `runner_shin` 데이터 건수: **3건** &rarr; 공격 요청 후 데이터 건수: **3건 (불변)**
- 공격 요청 전 `reviewer_guest` 데이터 건수: **2건** &rarr; 공격 요청 후 데이터 건수: **2건 (불변)**
- 변조된 데이터 건수: **0건 (`mutatedCount: 0`)**

### (4) 타인 계정 파라미터 위조 시에도 내 자료만 반환되는 방어
만약 일반 비공개 볼트 조회 화면에서 주소창에 `?owner=reviewer_guest`를 임의로 입력하더라도, 서버는 토큰의 `sub/username`과 파라미터가 다르면 즉시 403으로 차단하며, 파라미터가 생략되면 토큰 소유자 본인의 데이터만 안전하게 반환합니다.
