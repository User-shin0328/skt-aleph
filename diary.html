🛡️ 보안 검증 샌드박스 (실시간 공격 방어 및 증적 도구)
서버 방어 엔진 활성

서버(Vercel Serverless Function)에 구현된 보안 계층을 직접 트리거하여 동일 비밀번호 솔트 분리, 폐기된 토큰 재사용 차단, 타인 자료 변조(IDOR) 차단, 무인증 호출 차단을 실시간으로 확인하고 화면을 캡처할 수 있는 도구입니다.

💻 보안 검증 요청 & 응답 트랜잭션 콘솔
* 상단의 보안 검증 시험 버튼을 클릭하면 실제 HTTP 요청 헤더, 서버 응답 코드, 응답 JSON 페이로드가 실시간으로 이곳에 출력됩니다.
* 모든 민감 토큰은 eyJhb...[생략]으로 마스킹 표기되며, 비밀번호 평문은 절대 출력되지 않습니다.
📘 인증 설계 및 구현 설명서 (6대 핵심 기준)
체계적 보안 아키텍처

본 다이어리에 인증을 부착한 방식과 기술적 근거, 보안 검증 결과 및 잔존 위험 분석을 6개 항목으로 명확히 정리한 기술 문서입니다.

1️⃣ 무엇을 골랐는가 (선택한 인증 방식과 암호화 알고리즘)
  • 비밀번호 저장: 단방향 솔트 해싱 알고리즘 PBKDF2-HMAC-SHA256 (반복 횟수 100,000회, 계정별 고유 32바이트 암호학적 랜덤 Salt).
  • 사용자 세션 인증: 무상태(Stateless) 기반 JWT (JSON Web Token, Bearer) — 서명 알고리즘 HMAC-SHA256, 만료 시간 24시간.
  • 토큰 무효화 메커니즘: 로그아웃 즉시 서버 인메모리 블랙리스트(revokedTokens)에 등록하여 만료 전이라도 즉시 401 차단.
2️⃣ 왜 골랐는가 (선택 배경 및 기술적 근거)
  • Vercel Serverless 무상태(stateless) 런타임 최적화: 분산 컨테이너 환경에서 세션 스토리지를 별도 유지하지 않고도 서명 검증만으로 인가 처리가 가능합니다.
  • 외부 종속성 배제 및 공급망 보안 강화: Node.js 표준 crypto 라이브러리만을 사용하여 npm 패키지 변조나 공급망 취약점을 원천 차단했습니다.
  • GPU 무차별 대입 공격(Brute-force) 저항성: 단순 MD5/SHA-256과 달리 PBKDF2의 10만 회 키 스트레칭은 레인보우 테이블 및 병렬 연산 공격을 경제적으로 무력화합니다.
3️⃣ 소스의 어디를 고쳤는가 (핵심 수정 위치 및 파일)
  • api/diary.js (라인 40~180): hashPassword, verifyPassword, signJwt, verifyJwt, extractBearerToken 함수 구현, revokedTokens 블랙리스트 세트 관리.
  • api/diary.js (라인 220~380): 액션별(register, login, logout, delete_account, test_idor, verify_hashes) 핸들러 분기 및 IDOR 소유권 대조 미들웨어 적용.
  • diary.html (라인 1100~2400): 미인증 시 Auth Gate 전면 노출, 모든 API 호출 시 Authorization: Bearer 자동 첨부, 5일간 러닝 테이블 렌더링.
4️⃣ 무엇을 직접 확인했는가 (직접 검증한 보안 시나리오 4종)
  • 동일 암호 해시 상이성 확인: 동일 비밀번호(P@ssw0rd123!)로 생성된 2개 계정이 서로 다른 Salt와 Hash를 가짐을 실시간 대조.
  • 로그아웃 토큰 차단 확인: 로그아웃 즉시 발급된 토큰으로 재호출 시 401 TOKEN_REVOKED 응답 수신 확인.
  • IDOR 타인 리소스 침범 차단 확인: runner_guest 토큰으로 runner_shin의 할 일 수정을 시도하여 403 FORBIDDEN_DATA_ACCESS 및 데이터 변조 0건 확인.
  • 무인증 호출 차단 확인: 토큰 미포함 요청 시 401 AUTH_REQUIRED 수신 확인.
5️⃣ 아직 못 막은 것은 무엇인가 (잔존 취약점 및 한계점 솔직 고백)
  • IP 기반 무차별 대입 공격(Brute Force) 제한 부재: 현재 로그인 엔드포인트에 초당 시도 횟수를 제한하는 Rate Limiter가 미구현되어 있어 분산 사전 공격에 취약할 수 있음.
  • 브라우저 스토리지 XSS 탈취 위험: 클라이언트 편의를 위해 JWT를 sessionStorage에 보관하므로, 만약 XSS 취약점이 존재할 경우 스크립트에 의해 토큰이 탈취될 잠재적 위험이 있음.
  • 서버리스 콜드스타트 시 인메모리 블랙리스트 초기화: Vercel 함수가 새 인스턴스로 교체될 경우 서버 메모리에 있던 revokedTokens가 휘발될 수 있음.
6️⃣ 앞으로 어떻게 보완할 것인가 (단계별 고도화 로드맵)
  • Redis (Upstash) 기반 전역 Rate Limiting: 동일 IP당 1분간 최대 5회 로그인 실패 시 15분간 차단하는 지능형 잠금 적용.
  • HttpOnly, Secure, SameSite Cookie + Refresh Token: 액세스 토큰은 메모리에만 유지하고 리프레시 토큰은 HttpOnly 쿠키로 격리하여 XSS 토큰 탈취 원천 차단.
  • 영속적 토큰 블랙리스트 DB화: 인메모리 대신 Redis 또는 KV 데이터베이스에 폐기된 JTI(토큰 고유 식별자)를 TTL과 함께 저장하여 인스턴스 재부팅 후에도 폐기 상태 영구 보존.
